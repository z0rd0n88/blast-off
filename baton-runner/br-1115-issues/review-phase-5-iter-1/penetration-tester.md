#### MEDIUM

- **Title:** PT5-1. `preflight` reads a leading-zero `JOB_MAX_CHILDREN` as octal and `run` reads it as decimal: `010` shows the wrong number left, and `08` or `09` aborts preflight with no verdict
- **Location:** `lib/preflight.sh:32` (`local left=$((MAXC - LAUNCHED + (CAP_SOFT ? b : 0)))`, new); `lib/chain.sh:105,109` (`MAXC="$JOB_MAX_CHILDREN"` / `"${JOB_MAX_CHILDREN:-12}"`, copied as text); `lib/chain.sh:194` (`[ ... -gt "$MAXC" ]`, decimal); `lib/chain.sh:91` (`^[0-9]{1,9}$` accepts leading zeros); `phase-5/findings.md:15` and `baton-phase-5-work.md:60` ("leading zeros keep their old behaviour")
- **Failure path:** `JOB_MAX_CHILDREN=010 blast-off preflight <job>` on a fresh job prints `child-count: none, a fresh job; first child 1; 8 left under cap 010`. But `run`'s cap test is `[ $((n - ...)) -gt "010" ]`, and the `test` builtin parses `010` as decimal 10, so the run launches 10 children. With `JOB_MAX_CHILDREN=08`, or `09`, under either cap, preflight hits `$((08 - ...))` and bash prints `08: value too great for base (error token is "08")`. The non-interactive shell exits 1 there. The lines after `cap:` (`timeout`, `account`, `usage`, `estimate`, PRs, `behind`) and the `preflight: ok` / `preflight: refused:` verdict are never printed. Meanwhile `start` and `run` accept `08` and cap at 8. The work unit's claim that leading zeros "keep their old behaviour" is true for `JOB_CAP_FACTOR`, which was already in arithmetic at `chain.sh:107`. It is false for `JOB_MAX_CHILDREN`, which no arithmetic read before this change. This is the one case where preflight's "left" does not match `chain_run`'s cap test.
- **Evidence:** I probed it with `bash -c`. `local MAXC=010; ... $((MAXC - L + (CAP_SOFT ? b : 0)))` prints `left=8`, while `[ 9 -gt "010" ]` is false (decimal 10). For `MAXC=08`, the probe printed `environment: line 1: 08: value too great for base (error token is "08")` and `rc=1`, and the lines after it never ran. `[ 9 -gt "08" ]` is true (decimal 8). No test feeds preflight a leading-zero value.
- **Suggested fix:** Reject leading zeros once, where every caller passes: `chain_nums` regex `^(0|[1-9][0-9]{0,8})$`. That is the same shape `chain_count` already uses at `chain.sh:124`. It also closes the pre-existing `JOB_CAP_FACTOR=08` abort the work unit noted. Or use `$((10#$MAXC ...))` in preflight. Add `JOB_MAX_CHILDREN=08` to test 21's bad-number loop, or to a test-60 case.

- **Title:** PT5-2. P4R1-5 is closed only after the fact: a `child-count` deleted or rewritten by the last child of a run still resets the hard cap on the next relaunch, which can come from the resume timer with no owner involved. The new log line records the reset but does not stop it
- **Location:** `lib/chain.sh:122` (missing file means a fresh job), `:160` (the new `log "$COUNT_SAY"`), `:204` (the only save, before each launch); `lib/chain.sh:66` (job-dir files are skipped by the dirty-tree check); `docs/spec.md:61` and `README.md:136` ("the one deliberate reset"); `phase-5/findings.md:11`
- **Failure path:** The runner writes `child-count` only before a launch (`:204`). Nothing rewrites it after a child, so whatever the last child of a run leaves there persists. A confused child is in scope, and P4R1-5 in phase 4 listed its ways to do this: a cleanup of untracked files, following the garbled message's own advice "delete it to count this job's children from 0 again", or writing `0 0`. Hand-traced on a hard-cap job:
  1. Child 12 of 12 deletes or zeroes `child-count`. The job dir is exempt from the dirty-tree check, so nothing flags it.
  2. The run ends: exit 4 at the cap, or a usage limit that sets `paused-limit` and arms the resume timer (exit 8).
  3. The timer runs `resume` -> `start` -> `run`. `chain_count` reads "none" (or `0 0`), so the job restarts at child 1 with a full hard cap. The only trace is `child-count: none, a fresh job; first child 1` in `run.log`, written as the reset happens.
  The owner ruling P4R2-11 makes deletion the owner's reset. It does not make an unattended reset acceptable, and the hard cap is the runaway guardrail. The docs now call deletion "the one deliberate reset", but this path is neither deliberate nor done by the owner.
- **Evidence:** `chain_count_set` is called only at `chain.sh:171` (paused-cap, soft) and `:204` (before launch). No call follows `child_wait` at `:206`, or anywhere in `:207-239`. Test 10 pins the log line (`10:76`, `10:85`) but no test covers a file changed by a child.
- **Suggested fix:** One line. Call `chain_count_set` again after the child is stopped, for example after `child_clean` at `:225`, so the runner's in-memory `LAUNCHED BASE` overwrites whatever the child left. That closes every case except a runner killed mid-child. A stronger fix is a runner-owned copy outside the job dir, which the child is told to work in (`$XDG_STATE_HOME/blast-off/<unit>.count`), refusing to start when the two disagree. Or cross-check against the highest `child N launched` in `run.log`; the work unit explicitly declined that. To test it, give a fake child a mode that deletes `child-count`, then check that a re-run at the same hard cap exits 4.

#### LOW

- **Title:** PT5-3. `COUNT_ERR` embeds the raw file contents, with no length limit and no filtering, into `run.log`, the journal and now the owner's terminal through `status` and `preflight`
- **Location:** `lib/chain.sh:123` (`c="$(cat "$f" 2>&1)"`, whole file in memory), `:125` (`holds '$c'`), `:142` (`log`), `lib/preflight.sh:35`, `lib/units.sh:74`. Compare `lib/usage.sh:33`, which logs untrusted file bytes as `head -c 200 "$f" | tr '\n' ' '`.
- **Failure path:** A multi-line `child-count` writes extra lines into `run.log` with no timestamps. They can look like runner lines (`child 5 launched`, `job done`), which misleads anyone reading or grepping the log. ESC sequences reach the owner's terminal through `blast-off status` or `blast-off preflight`. Before this change, the message went only to the runner's stderr. A file of 1 GB is read whole into the shell and then appended to `run.log` and the journal. A malicious child is out of scope (owner ruling 3), and the checkpoint header that `status` prints is an equal channel, so this is LOW. A confused child that dumps output into the wrong file is the realistic case.
- **Suggested fix:** Reuse the usage.sh pattern: `c="$(head -c 64 "$f" 2>&1 | tr -c '[:print:]' '?')"` before the regex, then match the cleaned value. A valid count is at most 19 bytes. Combine this with PT5-4's regular-file check.

- **Title:** PT5-4. A FIFO, a character device or a huge file at `child-count` hangs or exhausts memory in `run` before the lock, and now also in `status` and `preflight`
- **Location:** `lib/chain.sh:122-123` (`[ -e ] || [ -L ]`, then `cat`); new callers `lib/units.sh:74` and `lib/preflight.sh:30`
- **Failure path:** `mkfifo child-count` passes `-e`, and `cat` blocks forever. A `run` started by `start` stays active with no child, no lock and no EXIT trap; `blast-off stop` ends it. `blast-off status`, the command an owner runs to see why, also hangs. So does `preflight`. A symlink to `/dev/zero` or `/dev/urandom` makes `$(cat)` grow until the process is killed for memory. In `run`, a FIFO also hung before this change. In `status` and `preflight` it is new.
- **Suggested fix:** After the existence check, add `[ -f "$f" ] || { COUNT_ERR="$f is not a regular file"; return 1; }`. `-f` follows a symlink, so a link to a real file still reads, and a link to a FIFO, device or directory is refused. Then read with `head -c 64`.

- **Title:** PT5-5. The refusal is written before the lock, so a second runner refused for a garbled count appends its refusal to the live runner's `run.log`. The line has no marker that says it was a refusal
- **Location:** `lib/chain.sh:142` (refusal) versus `:151` (`chain_lock`) and `:152` (trap); `bin/blast-off:47` (`log` has no prefix, unlike `die`'s `blast-off:`)
- **Failure path:** (a) A runner is live and something garbles `child-count` mid-run. A second `run`, from the resume timer or the owner, appends `.../child-count holds 'x', ...` to the live `run.log` and exits 1. It never reaches the lock check, so the reader sees a refusal in the middle of a healthy run, and the "another runner holds the lock" message never appears. The live runner then overwrites the file at its next launch, so the refusal points to a state that no longer exists. (b) The refusal exits before the EXIT trap, so `run.log` gets no `runner exit 1 ...` line, consistent with the other usage errors. But the line starts with a timestamp and the path. Nothing in it says "refused" or "exit 1", so `tail -f run.log` readers, whom README:84 promises "refusals", must infer it. (c) `LOG` is always set: `job_init` sets it at `bin/blast-off:61` before `chain_run`, and a missing job dir dies in `job_init` first. When `run.log` cannot be written, `tee -a` fails, `set -e` (active in the `||` right-hand group) exits with tee's status 1, and stderr still carries the message plus tee's error. Exit 1 holds either way. The work unit called (a) harmless, and it is low impact.
- **Suggested fix:** Prefix the line: `log "refused: $COUNT_ERR (exit 1, nothing started)" >&2`. Moving the check after `chain_lock` would also stop (a). It needs care, though, because the EXIT trap would then add a `runner exit 1 without a state` line and stop child scopes, so it should stay as it is unless the owner wants that.

- **Title:** PT5-6. Test 50's `grep -n 'child 2' | head -n 1` is a positional loose match that the new `next child N` line can satisfy. It is safe today only because test 50 uses fresh jobs
- **Location:** `tests/50-checkpoint-size.sh:37`; new line at `lib/chain.sh:160` (`child-count: L launched, base B; next child L+1`)
- **Failure path:** I grepped every scenario for run.log matches on `child [0-9N$]` without `launched`, `head -n 1`, `tail -n 1` and `grep -c`. Test 50:37 is the only positional loose match. On a job starting from `1 0`, the line `next child 2` comes before any child line and before the over-150 warning, so `[ "$w" -lt "$c2" ]` would fail, a false failure. `'child 2'` also matches `child 20`, `child 21` and so on. Every other match is safe: `'child [0-9]* launched'` (test 10:84,155,165; test 21:30,61) needs `child ` followed by ` launched`, and the new lines read `child-count: 1 launched` and `next child 2` at the end of the line. The `child 1 ...` greps in tests 20, 22 and 30 all carry a suffix the new line lacks. Test 30's `logt` (`:131-132`) anchors on `child 2 launched`. `tail -n 1` (test 10:174) is unaffected. All jobs come from `new_job`, which uses a new dir each time (`tests/lib.sh:21-28`). Production code does not parse `run.log` at all (`lib/jev.sh:67` only names it).
- **Suggested fix:** In test 50, anchor the grep: `grep -n 'child 2 launched'`. This is a latent risk, not a current failure.

- **Title:** PT5-11. The docs' "the one deliberate reset" is not the only reset: editing the file to a smaller valid count, which the refusal message invites ("fix it"), also resets

- **Title:** PT5-12. Preflight prints `N left` for jobs the run will not cap: `done`, `blocked`, and `paused-limit` before its reset. A capped job still gets `preflight: ok` (the rest of P4R1-3)

- `chain_count` returns instead of dying: sound. All three callers guard it (`chain.sh:142` `||`, `preflight.sh:30` `if`, `units.sh:74` `if`), so `set -e` is off inside it, and no other failure can occur in its body.
